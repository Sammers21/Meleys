# Borrow TechEmpower's tests, not its leaderboard

**TechEmpower is no longer an option for Meleys: TechEmpower shut down its Framework Benchmarks (TFB) and archived the repository read-only on 2026-03-24, Round 23 is the final round, and no new framework can be listed.** Even before the shutdown, TFB measured only peak cleartext HTTP/1.1 throughput for tiny GET responses on Linux, in closed-loop 15-second wrk runs, and its results showed no latency percentiles, no memory, no TLS, HTTP/2 or HTTP/3, and nothing for macOS or Windows, so at best it could have backed a small part of the Meleys vision. The better move is to borrow TFB's well-known JSON and plaintext tests as one module of a public lab that Meleys runs itself: two bare-metal Linux machines running closed-loop sweeps for throughput, open-model fixed-rate runs for p99 to p99.99 latency, h2load for HTTP/2 and HTTP/3, and whole-process RSS under pinned JVM settings, with raw data and a reproduce command behind every published number. Around that lab, JMH microbenchmarks tracked in Bencher catch regressions on every change, nightly change-point detection catches drift, and smaller Windows and macOS tiers track regressions without making headline claims. For an independent scoreboard, HttpArena is the natural venue: it is young, but it is the only active suite found that covers HTTP/1.1, HTTP/2 and HTTP/3 with p99, CPU and memory. The hardest claims to back will be HTTP/3 tail latency, because no mature open-model HTTP/3 load generator exists, and small memory footprint, because JVM memory numbers mostly reflect heap settings unless those are fixed. A Linux client/server pair costs roughly €115–515 a month and the CI tiers are free, and the payoff is data that none of the surveyed Java projects publishes today: p99.9, HTTP/3 and Windows numbers that anyone can reproduce.

## TechEmpower is archived, and it never measured most of Meleys's goals

### Round 23 is final, and submissions closed in March 2026

TechEmpower announced the end in GitHub issue #10932, "Sunsetting the TechEmpower Framework Benchmarks", opened and pinned on **2026-03-24**; the repository was archived read-only the same day, and the issue says only that "the repository, history, and past results remain as a snapshot" ([GitHub issue #10932](https://github.com/TechEmpower/FrameworkBenchmarks/issues/10932)). No public source gives a reason, which one Hacker News commenter complained about directly ([Hacker News](https://news.ycombinator.com/item?id=47497763)), and the stop was abrupt: new frameworks were still being merged on 2026-03-10 ([TFB merged pull requests](https://github.com/TechEmpower/FrameworkBenchmarks/pulls?q=is%3Apr+is%3Amerged+add+in%3Atitle+created%3A%3E2025-03-01)). **Round 23 is the final official round.** Its data come from a continuous run between 2025-01-30 and 2025-02-06 on code frozen on 2025-01-23, it was published on 2025-03-17, and its Java entries ran JDK 8 through 22 ([Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json); [Round 23 blog](https://www.techempower.com/blog/2025/03/17/framework-benchmarks-round-23/)). There is no Round 24, and on 2026-10-21 the continuous-results dashboard returned HTTP 503 while the Round 23 file still downloaded ([tfb-status](https://tfb-status.techempower.com/)). That settles the venue question: **Meleys cannot be listed**, and the newest public data describe code about 21 months old. Nothing public says how long the results site will stay online, and no fork continuing TFB has appeared.

TFB gave slow feedback even when it was alive: official rounds came 15 to 16 months apart, and one full continuous run took about 156 hours ([TFB results site](https://www.techempower.com/benchmarks/); [Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)). Two useful things survive. One is a BSD-style toolset that anyone can run privately ([TFB license](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/LICENSE)); the other is a body of competitor code, since Round 23's 841 permutations include **145 Java entries across 51 frameworks**, each with source and a Dockerfile ([Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)). The ASP.NET team still runs TFB's plaintext, JSON and Fortunes scenarios on its own machines, so the test definitions have already outlived the leaderboard ([ASP.NET Core benchmarks guide](https://github.com/dotnet/aspnetcore/blob/main/docs/Benchmarks.md)). A self-run "TFB score" for Meleys still could not be compared with the published table. Round 23 ran on three HPE ProLiant DL360 Gen10 Plus servers with 28-core Xeon Gold 6330 CPUs and 40 GbE cards provided by Microsoft, and that hardware, mainly the jump from 10 GbE to 40 GbE, lifted the best plaintext result from **about 7.0 million to 28.4 million requests per second** ([TFB results-site bundle](https://www.techempower.com/benchmarks/assets/index-rdjV3uRt.js); [Round 22 results JSON](https://www.techempower.com/benchmarks/results/round22/ph.json); [Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)). Ratios between frameworks measured on the same hardware carry over to other setups; absolute numbers do not.

TFB's defenders have a point about visibility. MongoDB's lead performance engineer treated a collapsed Spring/MongoDB result as a bug report and lifted the query test from 583 to 14,200 requests per second ([TechEmpower blog, 2026-03-16](https://www.techempower.com/blog/2026/03/16/how-our-benchmarks-led-to-a-25x-mongodb-performance-improvement/)), and PostgreSQL contributors used the lab to measure a roughly 9% libpq gain ([pgsql-hackers](https://www.postgresql.org/message-id/fdbf4c41-37ea-9da5-46c5-4c167ac79e8a%40gmail.com)). Both wins came from a live, shared lab that exposed large outliers, which is exactly what no longer exists and what Meleys can rebuild for its own code.

### Even at its peak, TFB tested only cleartext HTTP/1.1 throughput

All seven TFB test types are HTTP/1.1 GET requests with tiny bodies, such as a 28-byte JSON object or "Hello, World!". wrk drives each one with a 5-second primer, a warm-up and **one 15-second measurement per concurrency level** from 16 to 512 connections, while plaintext runs 256 to 16,384 connections with requests pipelined 16 deep ([TFB test requirements](https://github.com/TechEmpower/FrameworkBenchmarks/wiki/Project-Information-Framework-Tests-Overview); [run-tests.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/run-tests.py); [pipeline.lua](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/wrk/pipeline.lua)). The toolset builds only plain `http://` URLs and has no TLS, HTTP/2 or QUIC configuration, every Round 23 permutation ran Linux in Docker, and the Round 23 Vert.x entry even switched HTTP/2 cleartext off with `-Dvertx.disableH2c=true` ([framework_test.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/benchmark/framework_test.py); [Round 23 vertx.dockerfile](https://github.com/TechEmpower/FrameworkBenchmarks/blob/523534bb61450e3522d775a749ad060753e26e3a/frameworks/Java/vertx/vertx.dockerfile)). The results parser keeps only wrk's average, standard deviation and maximum latency, so **the results website never showed a percentile**; the toolset did record host and container memory, but a TechEmpower maintainer said in 2018 that the project did "not render these in any way" ([results.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/utils/results.py); [Hacker News, 2018](https://news.ycombinator.com/item?id=17254152)).

The latency TFB did publish says nothing useful about a p99 goal. wrk is closed-loop: each connection waits for a response before sending again, so the generator stops sending exactly when the server stalls. Gil Tene calls this coordinated omission, and in his wrk2 demonstration a single 1.4-second stall made the corrected p99 **200 times larger** than the uncorrected one ([wrk2 README](https://github.com/giltene/wrk2)). At saturation, closed-loop latency is mostly time spent queueing. By Little's law, 16,384 connections each holding 16 pipelined requests keep about 262,000 requests in flight, which at Round 22's ceiling of 7 million requests per second means an average near 37 ms however quickly the server handles each request. Round 23's own data show what such averages hide: three of the top Java JSON entries at 512 connections averaged 162–167 µs, yet their maximums ranged from 1.87 ms for smart-socket to **47 ms for edap-http-fast** ([Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)).

The top of each chart mostly measured the limits of the test setup rather than the frameworks. In Round 23, 11 realistic plaintext entries finished within 3% of a leader whose 28.4 million requests per second equal roughly 37 Gbit/s of request bytes on a 40 GbE link, and five JSON entries finished within 3% ([Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)); GenHTTP's maintainer says wrk and the request headers capped the plaintext top tier near 30 million requests per second ([DEV Community](https://dev.to/kaliumhexacyanoferrat/techempower-framework-benchmarks-are-now-archived-whats-next-3l0a)). The database tests largely ranked Postgres drivers: TechEmpower itself found in 2018 that results were "stratified" by driver-level query pipelining, the Vert.x entry sets a pipelining limit of 256, and 14 entries finished within 3% of the leader on the 20-query test ([Round 17 blog](https://www.techempower.com/blog/2018/10/30/framework-benchmarks-round-17/); [Vert.x TFB App.java](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/frameworks/Java/vertx/src/main/java/vertx/App.java)). The composite score applies "subjective weights" to six tests, four of which depend on the database ([Round 19 blog](https://www.techempower.com/blog/2020/05/28/framework-benchmarks-round-19/); [TFB composite scoring](https://github.com/TechEmpower/FrameworkBenchmarks/wiki/Composite-Scoring-for-Frameworks)). Plaintext also rewards HTTP/1.1 pipelining, which the rewrk authors note is "no longer enabled in most modern browsers or clients" ([rewrk README](https://github.com/lnx-search/rewrk)).

The rules relied mostly on entries labelling themselves. Only **29 of 965** test configurations at the final commit declared themselves "Stripped", meaning shorn of features the benchmark does not exercise, and the verifier checked response shape, headers and query counts but never HTTP compliance or resilience ([TFB frameworks tree](https://github.com/TechEmpower/FrameworkBenchmarks/tree/master/frameworks); [verifications.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/test_types/verifications.py)). When a contributor restarted the database under the top 20 entries in 2024, **only 8 recovered**, both Vert.x entries stayed stuck returning 500 and 502 errors, and TechEmpower closed the issue without changing a rule ([TFB issue #8790](https://github.com/TechEmpower/FrameworkBenchmarks/issues/8790)). The Java leaders reflect that culture. The best Java JSON entry, edap-http-fast at 96.8% of the leader, ran an OpenJDK 8u275 image with the obsolete `-XX:+AggressiveOpts` flag; most top Java entries were custom NIO servers rather than mainstream frameworks; and Spring's best JSON entry ranked 171st at 41% of the leader ([Round 23 Java tree](https://github.com/TechEmpower/FrameworkBenchmarks/tree/523534bb61450e3522d775a749ad060753e26e3a/frameworks/Java); [Round 23 results JSON](https://www.techempower.com/benchmarks/results/round23/ph.json)). Every entry also chose its own JDK, garbage collector and heap size, which rules out TFB-style memory comparisons, and TechEmpower's own FAQ concedes that "nothing beats conducting performance tests yourself" ([TFB Expected Questions](https://github.com/TechEmpower/FrameworkBenchmarks/wiki/Project-Information-Expected-Questions)). Set against each Meleys goal, the coverage gap looks like this:

| Meleys goal | What TFB measured | What Meleys needs instead |
|---|---|---|
| Highest throughput | Peak requests per second for tiny HTTP/1.1 GETs in 15-second runs; the top tier limited by the network | Closed-loop sweeps with CPU per request and core scaling, across all three protocols, TLS on and off, realistic payloads |
| Lowest latency, p99 and above | Average, standard deviation and maximum from closed-loop wrk at saturation | Open-model fixed-rate runs, full HdrHistogram percentile spectra, maximum sustainable throughput at p99 and p99.9 targets |
| Smallest memory, idle and under load | Recorded but never published; every entry chose its own heap | RSS at defined phases under fixed heaps, memory per connection, minimum-heap sweep |
| First-class HTTP/1.1, HTTP/2, HTTP/3 | HTTP/1.1 only, pipelined in plaintext | h2load across h2, h2c and h3, behind conformance checks |
| Newest JDKs | A frozen snapshot on JDK 8–22 | A matrix of JDK 25 LTS, JDK 27 and JDK 28 early-access builds |
| Linux, macOS, Windows | Linux in Docker | Linux for headline numbers; macOS and Windows regression tiers |
| Public, reproducible, against Java frameworks | Public, but one lab and now frozen | An open lab with raw data and reproduce commands, plus HttpArena |

## Fixed-rate load, not saturation, is the test of tail latency

Meleys's first two goals have to be measured under different conditions, so the lab needs two kinds of experiment. **Throughput** comes from closed-loop saturation sweeps over connection counts using wrk, cross-checked with bombardier or oha; wrk has had no commits since December 2023, but it is stable and it is the tool TFB used ([wrk on ecosyste.ms](https://repos.ecosyste.ms/api/v1/hosts/GitHub/repositories/wg%2Fwrk)). Each peak should be reported with the server's CPU-seconds per million requests and a sweep across core counts, because throughput loss alone understates cost: Gernot Heiser shows that if CPU rises from 60% to 100% while throughput falls 10%, the cost per request rose about 85% ([Systems Benchmarking Crimes](https://gernot-heiser.org/benchmarking-crimes.html)). **Latency** comes from open-model runs at fixed offered rates, from about 10% to 110% of the closed-loop maximum, with each request timed from when it should have been sent. Hyperfoil, a Java driver that "embraces Open System Model by default", qualifies, as do Vegeta's constant-rate attacks with HdrHistogram plots, oha run with `-q --latency-correction`, and k6's arrival-rate executors, which handle about 300,000 requests per second per instance ([Hyperfoil docs](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/_index.md); [Vegeta README](https://github.com/tsenart/vegeta); [oha README](https://github.com/hatoo/oha); [k6 large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)). The headline latency metric should be **maximum sustainable throughput at a target**, for example the highest offered load at which p99 stays under 1 ms and p99.9 under 10 ms, the framing ScyllaDB recommends ([ScyllaDB on coordinated omission](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)). Open and closed models give different answers even at identical load and service demand, so neither kind of experiment can stand in for the other ([Schroeder et al., NSDI 2006](https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf)).

Fast Java servers have tail latencies well below a millisecond, which is finer than some tools can resolve. wrk2's corrected latencies are accurate only to about ±1 ms ([wrk2 README](https://github.com/giltene/wrk2)), the timing resolution of Hyperfoil, oha and Vegeta is undocumented, and Jetty 12's core API measured a server-side p99 of **30 µs** ([Webtide: Jetty 12 performance figures](https://webtide.com/jetty-12-performance-figures)). Jetty's lab is therefore the design to copy: four load machines at 60,000 requests per second each, a separate probe at 100 requests per second that records latency, server-side HdrHistograms timing each request from first byte read to last byte written, one minute of warm-up and three of recording, flame graphs from every machine on every run, and latency assertions in the build ([Webtide: Jetty 12 performance figures](https://webtide.com/jetty-12-performance-figures); [Webtide: The Jetty Performance Effort](https://webtide.com/?p=4541)). jHiccup, run beside an idle control JVM, then separates pauses caused by the machine from pauses caused by the JVM ([jHiccup README](https://github.com/giltene/jHiccup)). The target percentile sets the run length: a p99.99 needs about a million samples to have 100 beyond it, roughly 100 seconds of steady state per load point at 10,000 requests per second. Below about 10 µs, client timing error dominates unless the client uses hardware timestamps as Lancet does, so Meleys should treat smaller differences as noise ([Lancet, USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/kogias-lancet)).

The hardware must not become what the benchmark measures. Headline numbers need a dedicated server and a separate, larger client on a real network link, never loopback; one large client is enough to start, with more load machines added when it nears saturation. TFB's history sets the bandwidth bar: about 7 million pipelined plaintext requests per second filled 10 GbE by Round 22, so a 1 GbE link would cap tiny-response tests near 0.7 million, far below what top Java servers reach, and 25 GbE or faster is the safe choice ([Round 16 blog](https://www.techempower.com/blog/2018/06/06/framework-benchmarks-round-16/); [Round 22 results JSON](https://www.techempower.com/benchmarks/results/round22/ph.json)). Hosts need the `performance` CPU governor, turbo boost off, the same SMT setting for every framework, one NUMA node, irqbalance off and isolated cores, with every setting recorded in each result ([pyperf system tuning](https://pyperf.readthedocs.io/en/latest/system.html); [LLVM benchmarking tips](https://llvm.org/docs/Benchmarking.html)). Cloud instances showed coefficients of variation from 0.03% to over 100% across Java and Go benchmarks, which makes cloud fine for breadth but not for claims ([Laaber et al., EMSE 2019](https://research.chalmers.se/en/publication/511491)). Connection-churn tests must budget for TIME_WAIT: when the client closes first, default port ranges and timers let one Linux client address open only about 470 new connections per second to a given server address and port, and a Windows client about 68, because Windows holds TIME_WAIT for four minutes ([Linux ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html); [Microsoft port exhaustion guide](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting)). Quarkus learned the cost of a loose setup in public, when its application and load generator shared CPU cores and made slower frameworks look competitive until community issue #55 forced a fix ([Quarkus blog](https://quarkus.io/blog/new-benchmarks/)).

Statistics then decide what counts as a win. One run should be a fresh JVM, a warm-up and one steady-state window, repeated at least 5 and preferably 10 times, because results vary between builds, launches and iterations ([Kalibera & Jones](https://kar.kent.ac.uk/33611/)). Medians with bootstrap confidence intervals, Mann–Whitney U tests, HdrHistograms merged across runs rather than averaged percentiles, and geometric means across scenarios keep comparisons honest ([HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram); [Heiser](https://gernot-heiser.org/benchmarking-crimes.html)). Each result should name what limited it, found by checking utilization, saturation and errors on both client and server during the run, because otherwise, as Brendan Gregg warns, "you benchmark A, but actually measure B, and conclude you've measured C" ([Gregg: Active Benchmarking](https://www.brendangregg.com/activebenchmarking.html)). Heiser also counts skipping the state of the art as a benchmarking crime, so a "fastest Java" claim needs the hard competitors: raw Netty, Vert.x, Helidon SE on its Níma server, Jetty 12's core API and the strongest custom TFB servers such as smart-socket and wizzardo-http, alongside Quarkus, Micronaut and Spring Boot. Their TFB implementations are a ready starting point but carry benchmark-specific settings, such as Jooby's disabled Netty header validation and bounds checks ([Round 23 Java tree](https://github.com/TechEmpower/FrameworkBenchmarks/tree/523534bb61450e3522d775a749ad060753e26e3a/frameworks/Java)), so each competitor should run twice: a "vendor" series following the project's documented production configuration, and a "normalized" series on Meleys's JDK and flags.

## HTTP/3 is the hardest Meleys claim to measure on the JVM

h2load, from the nghttp2 project, is the only mainstream load generator that drives HTTP/2 over TLS, cleartext h2c and HTTP/3 with matched semantics, controlling connections, streams per connection, flow-control windows, header tables, TLS groups and session resumption, and reporting median, p95 and p99 ([h2load manual](https://nghttp2.org/documentation/h2load.1.html)). Its HTTP/3 mode is **still experimental** and needs a custom build against ngtcp2 1.23.0 and nghttp3 1.17.0 or later ([nghttp2 README](https://github.com/nghttp2/nghttp2/blob/master/README.rst)). The alternatives fall short. oha's experimental HTTP/3 client topped out near 85,000 requests per second where an h2load HTTP/3 build reached about 580,000 against the same server ([HttpArena h2load-h3 notes](https://www.http-arena.com/docs/load-generators/h3/h2load-h3/)); Hyperfoil has no HTTP/3 and documents its h2c mode as "Currently not implemented" ([Hyperfoil HTTP docs](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/user-guide/benchmark/http.md)); and Vegeta covers h2 and h2c at a constant rate but not HTTP/3 ([Vegeta README](https://github.com/tsenart/vegeta)). **No mature open-model HTTP/3 generator that avoids coordinated omission exists**, and h2load's manual does not say whether its per-client `--rps` option corrects for it. HTTP/3 tail-latency claims therefore need a custom harness or careful runs at moderate load, with the client sized and monitored as carefully as the server, since receiving QUIC traffic drove Chrome to 97.4% CPU where HTTP/2 needed 77.1% in one study ([Zhang et al., WWW '24](https://arxiv.org/html/2310.09423v2)).

Test configuration swings HTTP/2 and HTTP/3 numbers more than server code does. h2load's defaults "effectively disable" flow control, so Meleys should also run with `-w16 -W16`, which restores the 65,535-byte windows that RFC 9113 specifies and real clients use ([h2load manual](https://nghttp2.org/documentation/h2load.1.html); [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)). Protocols should be compared at the same number of requests in flight; HttpArena runs HTTP/2 at 256 connections × 100 streams but HTTP/3 at 64 × 64, so its ratios mix protocol cost with load shape ([HttpArena baseline-h2](https://github.com/MDA2AV/HttpArena/blob/main/site/content/docs/test-profiles/h2/baseline-h2/implementation.md); [HttpArena baseline-h3](https://github.com/MDA2AV/HttpArena/blob/main/site/content/docs/test-profiles/h3/baseline-h3/implementation.md)). Key-exchange groups must be pinned, because JDK 27 now prefers the hybrid post-quantum group X25519MLKEM768 while h2load's default groups omit it ([JEP 527](https://openjdk.org/jeps/527)), and full, resumed and 0-RTT handshake rates belong in their own scenario. QUIC also needs a tuned Linux UDP path, with socket buffers raised to about 7.5 MB, segmentation and receive offload (GSO and GRO) confirmed in use, and qlog switched off, since logging "heavily" cuts throughput ([quic-go UDP buffer sizes](https://github.com/quic-go/quic-go/wiki/UDP-Buffer-Sizes); [Jaeger et al., IFIP Networking 2023](https://ar5iv.labs.arxiv.org/html/2309.16395)).

Expect HTTP/3 to cost more CPU, and expect the JVM to widen the gap. Independent studies since 2020 consistently find QUIC more expensive than TCP+TLS unless the stack batches packets aggressively: one measured QUIC data rates **up to 45.2% lower** than TCP+TLS+HTTP/2 because of receive-side packet processing ([Zhang et al., WWW '24](https://arxiv.org/html/2310.09423v2)), and another found that none of the open-source QUIC implementations matches TCP+TLS at 10 Gbit/s and above ([König et al., IFIP Networking 2025](https://doc.tm.kit.edu/2025-Examining-the-Heterogeneous-Throughput-Performance-Landscape-of-QUIC-Implementations-Koenig-et-al.pdf)). Across 30 HttpArena entries with both results, HTTP/2 beat HTTP/3 by a median factor of **2.65**, with nginx among the few exceptions and Ktor on Netty's quiche-based codec at 2.33 ([HttpArena results](https://github.com/MDA2AV/HttpArena/tree/main/site/data/results)). The JVM adds limits of its own. `DatagramChannel` and JDK 26's extended socket options expose no GSO or GRO ([JDK 26 ExtendedSocketOptions](https://docs.oracle.com/en/java/javase/26/docs/api/jdk.net/jdk/net/ExtendedSocketOptions.html)), Netty's QUIC segmentation works only on its Linux epoll transport ([Netty EpollQuicUtils](https://netty.io/4.2/api/io/netty/handler/codec/quic/EpollQuicUtils.html)), and OpenJDK's HTTP/3 client in JDK 26 explicitly excludes a server and a public QUIC API ([JEP 517](https://openjdk.org/jeps/517)). Jetty calls its quiche-based HTTP/3 "experimental", and pure-Java Kwik says its "performance is not optimal yet" under a GPL/LGPL license that fits poorly with an Apache-2.0 project ([Webtide on HTTP/3](https://webtide.com/?p=4270); [Kwik README](https://github.com/ptrd/kwik)). None of the Java projects surveyed publishes in-house HTTP/3 numbers. Meleys should benchmark its UDP layer on its own, in packets per second per core, and set a target that data can confirm or refute, such as **HTTP/3 within 2× of its own HTTP/2 at equal CPU and ahead of every other JVM HTTP/3 server**.

Conformance checks belong in front of every performance run, because a fast server that breaks the protocol wins benchmarks; HttpArena added HTTP/3 validation after finding that an HTTP/3-only entry "ran no assertions at all and still exited 0" ([HttpArena h3 validation](https://github.com/MDA2AV/HttpArena/blob/main/site/content/docs/test-profiles/h3/baseline-h3/validation.md)). The checks are h2spec in strict mode with JUnit output, h3spec for QUIC and HTTP/3 error cases, rule-breaking scripted clients built with Cloudflare's h3i, interoperability runs against the JDK 26+ HttpClient in `HTTP_3_URI_ONLY` mode, curl and h2load, and abuse tests under load such as HTTP/2 Rapid Reset (CVE-2023-44487) ([h2spec](https://github.com/summerwind/h2spec); [h3spec](https://hackage.haskell.org/package/h3spec); [h3i](https://docs.rs/crate/h3i/0.7.0); [Cloudflare on Rapid Reset](https://blog.cloudflare.com/technical-breakdown-http2-rapid-reset-ddos-attack/)).

## Memory claims are only as honest as the pinned JVM flags

The headline footprint number should be the **resident set size (RSS) of the whole process**, not the heap. Quarkus's performance lab records RSS with `pmap` after the first successful request, rejects `docker stats` because it counts only part of resident memory, and keeps Native Memory Tracking out of published runs because it costs 5–10% in performance ([Quarkus: Measuring performance](https://quarkus.io/guides/performance-measure)). For small footprints, JVM settings outweigh the application: a hello-world with a 16 MB heap commits about 75 MB, switching to the Serial collector halves that to 37.6 MB, and combined tuning reaches about 21 MB ([Shipilëv, JVM Anatomy Quark #12](https://shipilev.net/jvm/anatomy-quarks/12-native-memory-tracking/)). When heaps are not fixed, suites measure the JVM's default sizing rather than the frameworks, which is why HttpArena shows Quarkus at **10.4 GiB** and Helidon at **11.4 GiB** in its HTTP/2 test on a large shared host ([HttpArena results](https://github.com/MDA2AV/HttpArena/tree/main/site/data/results)). Suites that span languages show why the vision is right to compare only against Java frameworks: Sharkbench records Vert.x at 323 MB against 8.3 MB for Rust's hyper ([Sharkbench](https://sharkbench.dev/web)).

A credible footprint claim is a set of measurements taken at five points in the server's life: RSS and time to first request right after the first response; idle after warm-up and a full garbage collection; average and peak RSS at a fixed load below saturation; RSS at saturation; and idle again afterwards, which shows how much memory the JVM gives back. Memory per connection is the slope of RSS, heap and native memory while the server holds 0, 1,000, 10,000 and 100,000 idle connections over each protocol; the research found no primary data of this kind for any JVM server, so Meleys would set the reference. The DaCapo authors recommend evaluating collectors "across a range of heap sizes" expressed as multiples of the minimum heap a workload needs ([Blackburn et al., ASPLOS 2025](https://www.dacapobench.org/assets/pdf/dacapo-asplos-2025-with-appendix.pdf)). Binary-searching the smallest `-Xmx` that keeps latency on target at a fixed request rate, then reporting throughput, latency and RSS at 1.25×, 1.5×, 2× and 3× that heap, turns "smallest footprint" into a claim that can be checked and disproved. Runs that set `-Xms` equal to `-Xmx` with `AlwaysPreTouch` mostly report the configured heap and should never back a footprint claim.

JDK releases change the defaults a benchmark depends on, so every automatically chosen setting must be set explicitly. JDK 27, generally available since 2026-09-15, made G1 the default collector everywhere, where the JVM previously picked Serial on one CPU or under 1,792 MB, and switched on compact object headers by default, a feature that cut heap use 22% in one SPECjbb2015 setting ([JDK 27](https://openjdk.org/projects/jdk/27/); [JEP 523](https://openjdk.org/jeps/523); [JEP 534](https://openjdk.org/jeps/534)). The normalized series should therefore fix the JDK build, collector, `UseCompactObjectHeaders`, heap sizes, `-XX:ActiveProcessorCount`, transparent huge page mode and ahead-of-time (AOT) cache policy, and archive the `-XX:+PrintFlagsFinal` output with every run. AOT caches need results of their own: in JDK 28 early-access tests, an AOT cache holding ahead-of-time compiled code cut startup **65–80%** on five framework benchmarks, but only when the training run used the same collector and CPU features as production ([JEP 544](https://openjdk.org/jeps/544)). Cold start, warm-up curve and steady state belong in separate charts, and a matrix of G1, generational ZGC, Parallel and Serial at equal heap multiples is worth its cost because the evidence conflicts: DaCapo puts garbage-collection CPU overhead at 15% at best, while Netflix found generational ZGC improved average and p99 latency "with equal or better CPU utilization" than G1 ([DaCapo, ASPLOS 2025](https://www.dacapobench.org/assets/pdf/dacapo-asplos-2025-with-appendix.pdf); [Netflix Tech Blog](https://netflixtechblog.com/bending-pause-times-to-your-will-with-generational-zgc-256629c9386b)). For Netty-based competitors, record which transport ran, because the official native builds link against glibc, so an Alpine image or a missing native library leaves them on the slower NIO path ([Netty native transports](https://netty.io/wiki/native-transports.html)).

The cheapest repeatable metric is **bytes allocated per request**. JMH's `-prof gc` profiler reports it per operation as `gc.alloc.rate.norm`, and sampling `getTotalThreadAllocatedBytes()` against a request counter gives the same figure for a running server ([JMH profilers sample](https://github.com/openjdk/jmh/blob/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_35_Profilers.java); [ThreadMXBean, JDK 25](https://docs.w3cub.com/openjdk~25/jdk.management/com/sun/management/threadmxbean)). It depends far less on machine noise than throughput does, so it suits tracking on every commit, for each protocol path and handler model. Each lab run should also keep GC and safepoint logs stamped with JVM uptime and a default JFR recording that includes the `jdk.VirtualThreadPinned` event, so outliers in the latency histogram can be lined up against GC pauses, virtual-thread pinning and bursts of JIT compilation ([JEP 491](https://openjdk.org/jeps/491)).

## Build the lab in six prioritized steps

Mature projects keep a fast but noisy pull-request signal separate from authoritative runs on hardware they control, detect changes statistically, and assign people to triage regressions on a rotation, as Rust's weekly performance triage, ASP.NET's automatically filed `perf-regression` issues and MongoDB's rotating "Build Baron" show ([rustc-perf triage](https://github.com/rust-lang/rustc-perf/blob/master/triage/README.md); [dotnet/aspnetcore #57468](https://github.com/dotnet/aspnetcore/issues/57468); [Daly et al., ICPE 2020](https://arxiv.org/abs/2003.00584)). The plan below follows that pattern and orders the steps so each builds on the ones before it.

| Step | Set up | What it backs | Key tools and settings | When | Cost |
|---|---|---|---|---|---|
| 1 | A public benchmark repository and a written charter: claims stated as metrics, scenario catalog, competitor list, JVM normalization, a ban on benchmark-only code, reproducibility bundle | Every later number | TFB JSON and plaintext first; pipelined plaintext only as a labelled reference | Now | Free |
| 2 | JMH suite, hosted CI matrix, interleaved A/B runs, conformance checks | Per-pull-request regressions, bytes per request, protocol correctness | JMH with at least 2 forks and JSON output; Bencher; six pinned runner labels; h2spec, h3spec, h3i | From the first parser commit | Free |
| 3 | Two-machine bare-metal Linux lab | Headline throughput, p99 to p99.99, RSS | wrk sweeps; Hyperfoil or Vegeta at fixed rates; h2load with HTTP/3; RSS at five points; jHiccup; server-side histograms; vendor and normalized competitors | When Meleys serves HTTP/1.1 | €115–515 a month plus a fast link |
| 4 | Nightly lab runs, change-point detection, public dashboard, triage rotation | Long-term trends and openness | Self-hosted runner limited to trusted jobs; Apache Otava; raw JSON and histograms with reproduce commands | Once step 3 runs | Included in step 3 |
| 5 | Third-party venues | Independent visibility | HttpArena default and tuned entries; the-benchmarker; Sharkbench later | First public release | Free |
| 6 | Windows and macOS performance tier | The "every OS" goal | An owned Windows machine and an Apple-silicon Mac mini, weekly and per release; oha, bombardier, k6 or Hyperfoil | Before any cross-OS performance claim | One-off hardware |

**Step 1** costs nothing and guards against the ways TFB went wrong. The charter should define each claim as a measurable quantity (peak throughput with CPU per request, maximum sustainable throughput at p99 and p99.9 targets, and the five-point RSS measurements), forbid code paths that exist only for benchmarks, and list scenarios beyond TFB's: response sizes from 1 KB to 1 MB, POST bodies, many headers, slow clients, `Connection: close` churn, TLS handshake rates, large numbers of idle connections, HTTP/2 and HTTP/3 at matched in-flight counts, and routing tables of 10, 100 and 1,000 routes, a dimension no surveyed public suite tests. Pipelined plaintext stays a labelled reference result, as HttpArena treats it, and TFB's database tests are optional because they mostly rank Postgres drivers ([HttpArena README](https://github.com/MDA2AV/HttpArena)). Quarkus's comparison repository is a working template, with laptop, single-machine and lab tiers and separate out-of-the-box and tuned branches ([quarkusio/spring-quarkus-perf-comparison](https://github.com/quarkusio/spring-quarkus-perf-comparison)).

**Step 2** gives feedback while the server is young, but hosted runners catch only large regressions. CodSpeed measured an average coefficient of variation of 2.66% on GitHub-hosted runners against 0.56% on bare metal, so keeping false alarms to 1% needs a regression threshold of about **7%** ([CodSpeed](https://codspeed.io/blog/benchmarks-in-ci-without-noise)). Interleaving base and head builds in one job cut false alarms from 10–12.5% to 3.7% in Quansight's study ([Quansight Labs](https://labs.quansight.org/blog/github-actions-benchmarks)); multi-threaded workloads fare worst on hosted machines ([Reichelt et al., SSP 2024](https://arxiv.org/html/2411.05491v1)); one runner label landed on two different CPU models across ten identical jobs ([CodSpeed](https://codspeed.io/blog/unrelated-benchmark-regression)); and a runner-image kernel change once showed up as a regression with no code change ([Yang et al., 2025](https://arxiv.org/abs/2510.11310)). Hosted jobs should therefore run the JMH suite on pinned Linux, Windows and macOS labels for x64 and ARM64, block merges only on regressions above about 10%, and leave fine-grained tracking to Bencher, which is free for public projects, reads JMH's JSON output directly, applies per-branch t-test thresholds and handles pull requests from forks safely ([Bencher pricing](https://bencher.dev/pricing/); [Bencher adapters](https://bencher.dev/docs/explanation/adapters/); [Bencher GitHub Actions guide](https://bencher.dev/docs/how-to/github-actions/)). The alternatives are weaker for Java today: CodSpeed added Java only in May 2026, measures wall-clock time only and relies on a JMH fork not yet on Maven Central, and github-action-benchmark compares each result only with the previous one against a 200% default threshold ([CodSpeed Java docs](https://codspeed.io/docs/benchmarks/java); [github-action-benchmark](https://github.com/benchmark-action/github-action-benchmark)). JMH itself needs discipline: return every result or pass it to a Blackhole so the JIT cannot delete the work as dead code, read inputs from non-final `@State` fields so it cannot fold them into constants, and fork, as Netty's base class does with ten one-second warm-up and measurement iterations, two forks and JSON output ([JMH dead-code sample](https://github.com/openjdk/jmh/blob/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_08_DeadCode.java); [JMH constant-folding sample](https://github.com/openjdk/jmh/blob/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_10_ConstantFold.java); [Netty AbstractMicrobenchmarkBase](https://github.com/netty/netty/blob/4.2/microbench/src/main/java/io/netty/microbench/util/AbstractMicrobenchmarkBase.java)).

**Steps 3 and 4** produce the only numbers that should appear in claims. Hetzner's dedicated servers cost €57.30 to €257.30 a month, from EX44-1-LTD to AX102-1 machines, at prices in force since 2026-06-15, so a client/server pair runs about €115–515 a month; the cost of a 25 GbE link between them was not researched ([Hetzner price adjustment](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)). Orchestration can reuse ASP.NET's crank, which runs any Dockerfile job and whose scenario catalog already includes Netty, Vert.x and Spring, or Quarkus's Java-based pairing of Hyperfoil and qDup ([dotnet/crank](https://github.com/dotnet/crank); [aspnet/Benchmarks scenarios](https://github.com/aspnet/Benchmarks/blob/main/scenarios/README.md); [Quarkus blog](https://quarkus.io/blog/new-benchmarks/)). GitHub warns that self-hosted runners "should almost never be used for public repositories", so the lab machines must accept only pushes to main, scheduled jobs and maintainer-triggered jobs, never code from forks ([GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use)). Nightly results should go through change-point detection rather than fixed thresholds, since MongoDB's earlier 10% threshold system produced up to 99% false positives before it switched to E-Divisive change points ([Daly et al.](https://arxiv.org/abs/2003.00584)); Apache Otava, the incubating project descended from that work, is free ([Apache Otava](https://otava.apache.org/)). A weekly triage rotation with `perf-regression` labels and a three-day response target, as Mozilla runs, closes the loop ([Mozilla performance sheriffing](https://blog.mozilla.org/performance/2020/10/15/performance-sheriff-newsletter-september-2020/)), and publishing should follow ASP.NET, whose dashboard lists the exact command line behind each data point, with raw JSON and histogram logs beside every chart ([aspnet/Benchmarks scenarios README](https://github.com/aspnet/Benchmarks/blob/main/scenarios/README.md)).

**Step 5** buys independent visibility, with caveats. HttpArena, updated on 2026-10-20, runs 27 test profiles spanning HTTP/1.1, HTTP/2, h2c, HTTP/3, gRPC, WebSocket, TLS, connection churn and fixed-rate CPU-efficiency tests, reports requests per second, p99, CPU and memory, and benchmarks entries on its own hardware when a pull request triggers a run ([HttpArena](https://www.http-arena.com/); [HttpArena repository](https://github.com/MDA2AV/HttpArena)). On its HTTP/1.1 composite, Vert.x ranks 15th, Micronaut 28th, Quarkus 33rd and Spring Boot 70th ([HttpArena](https://www.http-arena.com/)). It is labelled an "Alpha Round", runs from a single GitHub account with 133 stars, keeps the best of three 5-second runs, and puts server and load generator on one 64-core machine over loopback, so it cannot back Meleys's tail-latency or memory claims ([HttpArena hardware](https://github.com/MDA2AV/HttpArena/blob/main/site/content/docs/hardware/_index.md)). Meleys should enter both a default and a tuned variant, as Helidon does, because tuned entries are left out of the default rankings and the default configuration is what gets judged ([HttpArena repository](https://github.com/MDA2AV/HttpArena)). the-benchmarker adds 21 Java competitors cheaply but tests only HTTP/1.1 routing, reports no memory and warns that results from its 2026 revisions cannot be compared with each other ([the-benchmarker](https://github.com/the-benchmarker/web-frameworks)), while Sharkbench admits only projects at least three months old with evidence of production use ([Sharkbench repository](https://github.com/sharkbench/sharkbench)). Rerunning the archived TFB toolset on Meleys's own hardware is optional, and any such numbers must be labelled self-run and unofficial.

**Step 6** supports the cross-OS goal without misleading anyone. Linux is the only platform with the full fast I/O path and diagnostic toolchain. macOS has no API to bind a thread to a CPU core, and its x64 port is deprecated for removal in JDK 28; on Windows, Java NIO runs on a wepoll-based selector, Netty has no native transport, async-profiler has no build, and loopback traffic falls back to a slow path whenever firewall filters are present ([XNU thread_policy.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread_policy.c); [JEP 541](https://openjdk.org/jeps/541); [JDK-8266369](https://bugs.openjdk.org/browse/JDK-8266369); [async-profiler](https://github.com/async-profiler/async-profiler); [Microsoft SIO_LOOPBACK_FAST_PATH](https://learn.microsoft.com/en-us/windows/win32/winsock/sio-loopback-fast-path)). GitHub's hosted Apple-silicon macOS runners are 3-vCPU M1 virtual machines with 7 GB of memory, and the research found no published noise data for hosted Windows or macOS runners ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Owned machines should run weekly and per release, comparing Meleys only with Java competitors on the same OS and never setting Windows or macOS numbers against Linux ones; how best to report JVM memory on Windows, as working set or private bytes, remains unresearched. ASP.NET shows the ideal setup, with Linux and Windows test machines of identical specification ([aspnet/Benchmarks scenarios](https://github.com/aspnet/Benchmarks/tree/main/scenarios)).

## Conclusion

With TFB gone, benchmark credibility no longer comes from a neutral leaderboard; it comes from data anyone can rerun and challenge. Quarkus's published results changed after community issues exposed shared CPU cores and an untuned Spring configuration ([Quarkus blog](https://quarkus.io/blog/new-benchmarks/)), which shows public correction now doing the job a neutral judge used to do, and Meleys should invite it by asking competitor maintainers to review their configurations before results ship. The same reasoning argues against chasing any single rank. Peak throughput is measured at saturation, tail latency below it and footprint at a fixed heap, so the honest form of "fastest, lowest latency, smallest" is a set of curves at stated loads, core counts and JVM settings, a form far harder to game than the rankings that undermined TFB.

Leading where nobody else measures carries its own risk: with no outside baseline, Meleys's measurement mistakes would go unnoticed unless conformance checks, A/A runs of identical builds and published raw data are treated as part of the product rather than overhead. Defaults are part of the product too. Venues such as HttpArena judge default entries as shipped, and users run what ships, so HTTP/2 window sizes, stream limits, UDP buffer sizes and heap guidance deserve the same optimization effort as the request parser. And because JDK 28's AOT-code and ZGC heap-sizing changes will move the numbers again, the lab's most lasting asset is not any single result but scripts that regenerate every published number on each new JDK.
