## 1. Which HTTP/1.1 load generators are trustworthy as of 2026, and for what?

### Takeaway
No single tool covers everything. Closed-loop tools are acceptable only for maximum-throughput or saturation numbers: wrk, bombardier, oha without `-q`, hey, rewrk, and autocannon without `-R`. Fixed-rate or open-model tools are needed for latency: wrk2, Hyperfoil, Vegeta, oha with `-q --latency-correction`, k6 arrival-rate executors, Gatling `injectOpen`, and autocannon with `-R`.

The two classic C tools are dormant. wrk was last pushed in Dec 2023 and wrk2 in Mar 2024, and wrk2's corrected latencies are only accurate to about ±1 ms. That makes wrk2 unsuitable for the sub-millisecond tails a fast Java server will show on a LAN. The actively maintained open-model options are Hyperfoil, Vegeta, k6, Gatling and oha.

**Load model, coordinated-omission handling, histograms, pipelining, client efficiency**
- **wrk**: "capable of generating significant load when run on a single multi-core CPU"; it "combines a multithreaded design with scalable event notification systems such as epoll and kqueue". It can be scripted in LuaJIT. — [wrk README](https://github.com/wg/wrk)
- **wrk** measures each request's latency "from the sending of the first byte of the request to the time the complete response was received". Each connection sends only after the previous response arrives, so wrk "exhibits a strong Coordinated Omission effect". wrk2 also "replaces wrk's individual request sample buffers with HdrHistograms", which means wrk itself does not use HdrHistogram. — [wrk2 README](https://github.com/giltene/wrk2)
- **wrk supports HTTP/1.1 pipelining through Lua**. Its repo ships `scripts/pipeline.lua`, which concatenates several requests and sends them as one write. — [wrk scripts/pipeline.lua](https://github.com/wg/wrk/blob/master/scripts/pipeline.lua). This **contradicts** the autocannon README, which states "`wrk` does not support HTTP/1.1 pipelining" — [autocannon README](https://github.com/mcollina/autocannon). TechEmpower itself drives wrk with `-s pipeline.lua` — [TFB pipeline.sh](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/wrk/pipeline.sh).
- **wrk2** "produce[s] a constant throughput load" set with `--rate`/`-R` (default 1000 requests/s). It aims to give "accurate latency details to the high 9s (i.e. can produce accurate 99.9999%'ile when run long enough)". It records into HdrHistograms and keeps wrk's Lua API. — [wrk2 README](https://github.com/giltene/wrk2)
- **wrk2 caveat**: "measured latencies are [only] accurate to a +/- ~1 msec granularity, due to OS sleep time behavior." — [wrk2 README](https://github.com/giltene/wrk2)
- **oha**: `-q` is a "Rate limit for all, in queries per second (QPS)". `--latency-correction` is documented as "Correct latency to avoid coordinated omission problem. It's ignored if -q is not set." The README recommends `oha <-z or -n> -c <conns> -q <qps> --latency-correction --disable-keepalive <url>` for "more realistic" tests, and says its defaults are "inherited from rakyll/hey". It supports HTTP/2 (`-p` parallel streams per connection) and has "experimental HTTP3 support" behind an `http3` feature that uses the hyperium `h3` library. It installs on macOS (Homebrew) and Windows (winget). — [oha README](https://github.com/hatoo/oha)
- **bombardier**: options include `-c, --connections=125`, `-r, --rate` ("Rate limit in requests per second"), `-l, --latencies` and `--fasthttp`. — [bombardier doc.go](https://github.com/codesenberg/bombardier/blob/master/doc.go). It uses fasthttp by default, and the `net/http` client (`--http1`/`--http2`) is needed for HTTP/2 or "a more RFC-compliant HTTP client". — [bombardier README](https://github.com/codesenberg/bombardier). Neither document mentions coordinated-omission correction.
- **hey**: `-q` is a "Rate limit, in queries per second (QPS) per worker"; `-h2` enables HTTP/2. Binaries are provided for macOS and Windows. The README does not mention coordinated-omission correction. — [hey README](https://github.com/rakyll/hey)
- **autocannon**: supports `-p/--pipelining`, `-R/--overallRate` and `-r/--connectionRate`. When a rate is set, "latency data will be corrected to compensate for the effects of the coordinated omission issue". `-C/--ignoreCoordinatedOmission` turns the correction off. Histograms are `hdr-histogram-percentiles-obj` objects. — [autocannon README](https://github.com/mcollina/autocannon)
- **autocannon client cost**: "it is CPU-bound… it uses significantly more CPU than other tools that compiles to a binary such as `wrk`", and the README recommends wrk2 when autocannon reaches 100% CPU. In its own example against Node.js at about 41k req/s, wrk used "20% + 20% + 40%" across 3 threads, while autocannon used "a single thread at 80% CPU load". — [autocannon README](https://github.com/mcollina/autocannon)
- **rewrk** is built on hyper's client, supports HTTP/1 and HTTP/2, and disables pipelining deliberately. Its motivation is that wrk/TechEmpower are "entirely biased towards frameworks and servers that can make heavy use of HTTP/1 Pipelining which is no longer enabled in most modern browsers or clients". It was "developed on Windows but will run on Mac and Linux as well." — [rewrk README](https://github.com/lnx-search/rewrk)
- **Vegeta** was "built out of a need to drill HTTP services with a constant request rate" and claims it "Avoids nasty Coordinated Omission". It has `-workers` (initial, default 10) and `-max-workers` (default effectively unlimited, 18446744073709551615). Its `report -type=hdrplot` output is "plottable by https://hdrhistogram.github.io/HdrHistogram/plotFiles.html". For distributed load, the README splits the rate across machines, and `vegeta report` "accept[s] multiple result files… sort[s] them by timestamp". — [Vegeta README](https://github.com/tsenart/vegeta)
- **k6**: "Some executors use the closed model, while the arrival-rate executors use the open model". In the closed model "VU iterations start only when the last iteration finishes… In some testing literature, this problem is known as coordinated omission." The open model is implemented by `constant-arrival-rate` and `ramping-arrival-rate`. — [k6 docs: Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/). With arrival-rate executors "iterations drop if there are no free VUs", and k6 counts them in the `dropped_iterations` metric. — [k6 docs: Dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)
- **k6 client capacity**: "a single instance of k6 can run 30,000-40,000 simultaneous users (VUs)… this number of VUs can generate up to 300,000 HTTP requests per second (RPS)". The docs also say "If k6 uses 100% of the CPU to generate load, the test will experience throttling limits". — [k6 docs: Running large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/)
- **Gatling**: injection profiles are defined with `injectOpen` and `injectClosed`. In the open model, `constantUsersPerSec(rate).during(duration)` "Injects users at a constant rate… at regular intervals", with a `.randomized` variant. The closed model uses `constantConcurrentUsers(n)`. — [Gatling docs: Injection](https://docs.gatling.io/concepts/injection/)
- **Hyperfoil** describes itself as a "microservice-oriented distributed benchmark framework that solves the coordinated-omission fallacy". Building it requires Java 21. — [Hyperfoil README](https://github.com/Hyperfoil/Hyperfoil). Its docs say it "embraces Open System Model by default - virtual users are completely independent until it runs out of resources, recording that situation in consequence… all requests are executed asynchronously". — [Hyperfoil docs: Overview](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/_index.md). Phase types: `constantRate`, `increasingRate` and `decreasingRate` are open-model; `always` is "a closed-model… similar to the way many benchmarks with fixed number of threads work"; `atOnce` is the third type. — [Hyperfoil docs: Phases](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/user-guide/benchmark/phases.md)
- **Hyperfoil architecture and client efficiency**: it uses a leader–follower design, where the Controller (a Vert.x server with a REST API) deploys agents and talks to them over the Vert.x event bus. It "pre-allocates all memory for the scenario execution ahead" to keep allocations low. — [Hyperfoil docs: Concepts](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/concepts.md). The FAQ admits JVM "jitter can be challenging" and says the team is "very careful on the execution hot-path". It also offers a `wrk`/`wrk2` facade CLI. — [Hyperfoil FAQ](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/faq.md)
- **JMeter**: the "Open Model Thread Group" generates users "according to the schedule", e.g. `rate(10/sec) random_arrivals(1 min) rate(10/sec)`. The component reference notes that "in many cases, Open Model Thread Group would be a better choice for generating the desired load profile". — [JMeter component reference](https://jmeter.apache.org/usermanual/component_reference.html#Open_Model_Thread_Group)
- **Locust** is user-based. Its `wait_time` options include `constant_throughput`, `constant_pacing` and `poisson`, but "Wait time can only constrain the throughput, not launch new Users to reach the target", so throughput drops if iterations take longer than planned. — [Locust docs: Writing a locustfile](https://docs.locust.io/en/stable/writing-a-locustfile.html)
- **Locust client cost**: in the best case, one Locust process on one CPU core "can do around 16000 requests per second using FastHttpUser, and 4000 using HttpUser (tested on a 2021 M1 MacBook Pro and Python 3.11)". The docs recommend one process per core. — [Locust docs: Increase performance](https://docs.locust.io/en/stable/increase-performance.html)
- **Academic framing**: Schroeder, Wierman and Harchol-Balter surveyed web workload generators and found "Most of these generators/benchmarks assume a closed system model". They wrote that "the 'choice' of a system model… is often not really a researcher's choice, but rather is dictated by the availability of the workload generator". — [Open Versus Closed: A Cautionary Tale, NSDI 2006](https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf)
- **How TechEmpower measures**: TFB runs **wrk** (closed-loop) with `--latency`. Each test starts with a 5 s "Primer" (8 connections, 8 threads), then a warm-up run at the maximum concurrency, then one run per concurrency level. — [TFB concurrency.sh](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/wrk/concurrency.sh). Defaults: `--duration` 15 s, concurrency levels [16, 32, 64, 128, 256, 512], pipeline concurrency levels [256, 1024, 4096, 16384], query levels [1, 5, 10, 15, 20]. — [TFB run-tests.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/run-tests.py). The plaintext test uses pipeline depth **16**. — [TFB plaintext.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/test_types/plaintext/plaintext.py)

- For Meleys' headline "fastest" claims, a practical pairing is: **wrk** for TFB-comparable max throughput (keep-alive, with and without pipelining), plus **Hyperfoil** (or wrk2 / Vegeta as cross-checks) for open-model latency-at-rate. If two independent tools agree on the max-throughput figure, a client-side artefact becomes unlikely.
- A fast Java server on a LAN will likely have p50 and p99 well under 1 ms, which falls below wrk2's documented ±~1 ms timing granularity. wrk2's tails are still useful against millisecond SLOs, but sub-millisecond percentiles need a client with finer timing. That could be Hyperfoil, oha or Vegeta, though their timing resolution is not documented (see Gaps). It could also be a Lancet-style setup with hardware timestamps (see Q2).
- TFB's latency columns come from wrk's coordinated-omission-prone measurement. TFB is therefore a throughput benchmark, not a tail-latency benchmark, and its pipelined plaintext test (depth 16) rewards pipelining-optimised servers in a way modern clients rarely exercise (rewrk's critique). The TFB repo is archived as of 2026, which should weigh on whether to build the project's benchmarking around it. TFB status is covered in more depth by another researcher.
- On Windows, wrk and wrk2 have no native backend: the README names only epoll and kqueue, not IOCP, so they would need WSL. Native Windows choices are oha, bombardier, hey, k6, Gatling, Hyperfoil (JVM), Vegeta and autocannon.

## 2. What is coordinated omission, how do wrk2 and Hyperfoil address it, and how should latency be presented?

### Takeaway
Coordinated omission (CO) happens when a load generator waits for slow responses before sending more requests. It then silently skips measuring exactly the requests that would have seen the worst latency, which can understate p99 by orders of magnitude (200× in wrk2's own demonstration).

The fix is to generate load on a schedule (open model) and to measure each request's latency from its *intended* send time. wrk2 does this with a constant-rate plan; Hyperfoil does it by starting virtual users independently on a schedule. Latency should be reported as full percentile spectra (HdrHistogram plots) at several fixed offered loads. The headline metric should be the maximum sustainable throughput that still meets a latency SLO, not raw maximum RPS.

### Cited Findings
- **Definition**: "Coordinated omission is a term coined by Gil Tene to describe the phenomenon when the measuring system inadvertently coordinates with the system being measured in a way that avoids measuring outliers." — [ScyllaDB blog, "On Coordinated Omission" (Apr 2021)](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)
- Gil Tene's canonical talk is "How NOT to Measure Latency" (InfoQ). The InfoQ page lists it as "Recorded at Mar 26, 2016" and also tags QCon San Francisco 2015, so the venue date is ambiguous. The talk covers "common pitfalls encountered (far too often) in the field" and "proven methodologies for measuring, reporting, and investigating latencies". — [InfoQ: How NOT to Measure Latency](https://www.infoq.com/presentations/latency-response-time/). Hyperfoil's docs link the 2013 slide deck. — [Azul slides PDF (as linked from Hyperfoil docs)](https://www.azul.com/files/HowNotToMeasureLatency_LLSummit_NYC_12Nov2013.pdf)
- **Mechanism (wrk2 README, written by Gil Tene)**: "Since each connection will only begin to send a request after receiving a response, high latency responses result in the load generator coordinating with the server to avoid measurement during high latency periods." — [wrk2 README](https://github.com/giltene/wrk2)
- **wrk2's fix**: it combines "constant throughput load generation with latency measurement that takes the intended constant throughput into account… wrk2 measures response latency from the time the transmission *should* have occurred". The README notes the technique "can be applied to variable throughput loaders" as long as there is a plan giving each request's intended start time. — [wrk2 README](https://github.com/giltene/wrk2)
- **Magnitude**: with `--u_latency`, wrk2 also reports the uncorrected histogram. In a "quiet" run (worst case 11 ms), p99 differed by about 2× between corrected and uncorrected. With a single 1.4 s stall (the Apache process paused with ^Z), the corrected p99 was "200x (!!!) larger" than the traditional measurement. — [wrk2 README](https://github.com/giltene/wrk2)
- **Why "just go async" is not a general fix**: completely asynchronous generators avoid CO, but that "is normally only effective with non-blocking protocols or single-request-per-connection workloads". HTTP/1.1 keep-alive connections carry serial request/response exchanges. — [wrk2 README](https://github.com/giltene/wrk2)
- **HdrHistogram post-hoc correction**: `recordValueWithExpectedInterval()` back-fills the samples that "should" have occurred. HdrHistogram's example: a system samples every 10 ms, takes 1 ms for 100 s, then stalls for 100 s. Raw data shows "~99.99% of results at 1 msec or below". The corrected histogram shows "~50%" at or below 1 ms, which is the right answer. — [HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram)
- **HdrHistograms are additive**: "since Histogram objects are additive, it is common practice to use per-thread non-synchronized histograms… and use a summary/reporting thread to perform histogram aggregation math across time and/or threads." — [HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram)
- **Scheduling taxonomy**: a schedule is either static (a function of start time) or dynamic. Missed sends can be queued or dropped ("queueless"). "The Queuing approach for a static schedule is the most reliable and correct… used in… YCSB, Cassandra-stress, wrk2". Global rate limiters with "burst = 0" are "susceptible to coordination with the target system". Latency correction counts client-side queue wait plus service time ("Latency consists of time spent waiting in the queue plus service time"). — [ScyllaDB blog](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)
- **Hyperfoil's approach**: many load drivers use "few dozen of virtual users (VUs) that execute one request after another… the Closed System Model… This discrepancy leads to problem known as coordinated omission and results in significantly skewed latency results and pathological conditions (queues overflow...) not being triggered." Hyperfoil uses the open model by default and records the situation when it "runs out of resources". — [Hyperfoil docs: Overview](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/_index.md)
- **Hyperfoil session sizing under stalls**: "if the server experiences a 3-second hiccup and we have 100 new users per second this should be at least 300 as all the users will be blocked". If the `maxSessions` estimate is exceeded, "new sessions will be allocated which might negatively impact results accuracy". An "Exceeded session limit" error means "the load at the tested system is too high and the responses are not arriving as fast as you fire the requests". — [Hyperfoil docs: Phases](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/user-guide/benchmark/phases.md); [Hyperfoil FAQ](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/faq.md)
- **Open vs closed matters beyond CO**: "closed and open system models yield significantly different results, even when both models are run with the same load and service demands… the two systems respond fundamentally differently to varying parameters and to resource allocation (scheduling) policies." The paper distils eight principles and recommends "partly open" models for some workloads. — [Schroeder et al., NSDI 2006](https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf)
- **Throughput at a latency target, not max RPS**: "With more requests and higher throughput, utilization climbs up to its limit of 100% and latency rises to infinity. The goal of benchmarking is to find the optimal point on that curve, where utilization (or throughput) is highest, with latency at or below the target level", e.g. "What is the maximum throughput of the system when the 99th latency percentile (P99) is less than 10 milliseconds (ms)?" — [ScyllaDB blog](https://www.scylladb.com/2021/04/22/on-coordinated-omission/)
- **On max throughput as a single number**: Hyperfoil's FAQ says "With too high concurrency you can get worse results due to contention and longer queues, so you need to try different concurrency level[s]". It adds that closed-loop max-throughput tests are fine "as long as you know what you're doing, and that the response latencies might be far off reality", and that they are "very good test[s] when you look only for regressions". — [Hyperfoil FAQ](https://github.com/Hyperfoil/Hyperfoil/blob/master/docs/site/content/en/docs/overview/faq.md)
- **Percentile-spectrum plotting**: Vegeta's `hdrplot` report emits data "plottable by https://hdrhistogram.github.io/HdrHistogram/plotFiles.html". — [Vegeta README](https://github.com/tsenart/vegeta)
- **Microsecond-scale tail measurement (research state of the art)**: LANCET measures "open-loop tail latency of μs-scale datacenter applications". It uses "online statistical tests to determine situations in which tail latency cannot be accurately measured". It sets "the length of the warmup phase, the measurement length, and the necessary sampling rate" dynamically, uses "NIC-based hardware timestamping" where available, and otherwise uses "a latency-agent that leverages busy-polling system calls to reduce the client bias". It reports p99 "with 95% confidence… within an interval of ≤ 10μs". — [Lancet, USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/kogias-lancet)

### Inferences
- **Presentation standard for Meleys:**
  1. For each offered load (requests/s), publish the full HdrHistogram percentile spectrum (p50 … p99, p99.9, p99.99, max) as a log-scale "percentile distribution" plot, with all frameworks overlaid at the *same* offered load.
  2. Publish a latency-vs-throughput curve: offered load on the x-axis, p50/p99/p99.9 on a log y-axis, plus achieved throughput and error rate.
  3. Report **maximum sustainable throughput (MST) at an SLO**: the highest offered load where p99 (and separately p99.9) ≤ target, errors ≤ budget, and achieved rate ≈ offered rate. Example targets are 1 ms and 10 ms at p99 on a LAN.
  4. Find the **knee** with a step ramp: for example 10% steps of the closed-loop maximum, then a binary search between the last passing and first failing step. Hyperfoil's `increasingRate` phases and iteration scaling, k6's `ramping-arrival-rate`, or repeated fixed-rate wrk2/Vegeta runs all work.
- Never average percentiles across runs or threads. Merge HdrHistograms, which are additive, or merge raw results (Vegeta sorts merged result files by timestamp). Separately show the run-to-run spread of each run's p99.
- When a tool exposes both corrected and uncorrected histograms (wrk2 `--u_latency`, autocannon `-C`), showing both once in the methodology section teaches readers why the project's numbers may look "worse" than other frameworks' published wrk numbers.
- A simple tail-amplification argument motivates p99+: if a page or API call fans out to N requests, the share of operations hitting at least one ≥p99 response is 1 − 0.99^N. That is about 63% for N = 100 (arithmetic, not from a source).
- Sample-size rule of thumb (arithmetic): a p99.99 estimate needs on the order of 10^6 samples to have about 100 observations beyond it. At 10k req/s that is about 100 s of steady state per load point. Lancet's approach shows how to make this rigorous with confidence intervals.
- Client-side queueing and timing bias matter at microsecond scale. Lancet uses busy-polling latency agents and hardware timestamps for that reason. Meleys should treat any sub-10 µs differences in tail latency as within client measurement error unless it uses such techniques.

## 3. How should runs be designed?

### Takeaway
Run two separate experiment families:
- **(a) Closed-loop saturation sweeps.** Use these for max requests/s and CPU cost per request at concurrency levels like TFB's 16–512, plus pipelined 256–16,384.
- **(b) Open-loop fixed-rate sweeps.** Use these for latency percentiles and MST at an SLO.

Each point needs a primer, a warm-up, a verified steady state and enough duration for the target percentile. Run keep-alive tests as the default and connection-churn tests as their own scenario, sized against ephemeral-port and TIME_WAIT budgets. The client must be a separate machine that is demonstrably not the bottleneck, and the network should be real rather than loopback.

### Cited Findings
- **TFB's run structure (a reference design)**: a 5 s primer at 8 connections, a warm-up at maximum concurrency for the full duration, then 15 s runs at each concurrency level, with 5 s and 2 s sleeps between runs and wrk `--timeout 8`. Threads are capped at `nproc`. — [TFB concurrency.sh](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/wrk/concurrency.sh); [TFB run-tests.py](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/run-tests.py)
- **Steady state and duration**: Gregg advises to "configure the benchmark to run for a long duration in a steady state: e.g., hours", and to analyse all involved components during the run "to identify the true limiter of the benchmark". — [Brendan Gregg: Active Benchmarking](https://www.brendangregg.com/activebenchmarking.html)
- **Automatic warm-up and length selection**: Lancet's coordinator sets "the length of the warmup phase, the measurement length, and the necessary sampling rate" using online statistical tests. — [Lancet, USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/kogias-lancet)
- **Common benchmark errors to design against**: "Throttled by the network between the benchmark client and the server", "Limited by the benchmark software being single threaded", "Perturbed by other system events, including neighbors", "Software resource controls" throttling, comparing different client/server software versions, and "An unrealistic workload". The core warning is "you benchmark A, but actually measure B, and conclude you've measured C." — [Brendan Gregg: Active Benchmarking](https://www.brendangregg.com/activebenchmarking.html)
- **Client saturation**: "If k6 uses 100% of the CPU to generate load, the test will experience throttling limits" — [k6 docs: Running large tests](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/). Autocannon "can saturate sooner because it is single-threaded" — [autocannon README](https://github.com/mcollina/autocannon). When a single Vegeta box hits "machine limits such as open files, memory, CPU or network bandwidth", the README recommends a distributed attack that splits the rate across machines — [Vegeta README](https://github.com/tsenart/vegeta).
- **Keep-alive vs churn**: oha's README argues "In real, user doesn't query same URL using Keep-Alive. You may want to run without Keep-Alive" (`--disable-keepalive`) — [oha README](https://github.com/hatoo/oha). TFB sends `Connection: keep-alive` — [TFB concurrency.sh](https://github.com/TechEmpower/FrameworkBenchmarks/blob/master/toolset/wrk/concurrency.sh).
- **Linux ephemeral ports**: `ip_local_port_range` defaults to 32768–60999 — [Linux ip-sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html). That is "more than 28,000 ports (60999+1-32768=28232)" — [Cloudflare: How to stop running out of ephemeral ports](https://blog.cloudflare.com/how-to-stop-running-out-of-ephemeral-ports-and-start-to-love-long-lived-connections/). Linux TIME_WAIT is hard-coded as `TCP_TIMEWAIT_LEN (60*HZ)` — [linux include/net/tcp.h](https://github.com/torvalds/linux/blob/master/include/net/tcp.h). `tcp_tw_reuse` defaults to **2 = "enable for loopback traffic only"**, and the docs say it "should not be changed without advice/request of technical experts" — [Linux ip-sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html).
- **Bind-before-connect pitfall**: Cloudflare explains that `bind()` before `connect()` reserves ports inefficiently. `IP_BIND_ADDRESS_NO_PORT` (Linux, 2015) "tells the kernel to delay reserv[ing]" the port. — [Cloudflare blog](https://blog.cloudflare.com/how-to-stop-running-out-of-ephemeral-ports-and-start-to-love-long-lived-connections/)
- **Windows ephemeral ports**: the default dynamic range is 49152–65535 (16,384 ports). After a connection closes, the port returns to the pool "after a period of 4 minutes (default)" in TIME_WAIT. — [Microsoft: TCP/IP port exhaustion troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/tcp-ip-port-exhaustion-troubleshooting)
- **macOS ephemeral ports and TIME_WAIT**: XNU defines `IPPORT_HIFIRSTAUTO 49152` and `IPPORT_HILASTAUTO 65535` — [XNU bsd/netinet/in.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in.h). It defines `TCPTV_MSL (15*TCP_RETRANSHZ)` as the max segment lifetime, i.e. 15 s — [XNU bsd/netinet/tcp_timer.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/tcp_timer.h).
- **CPU cost, not throughput loss, is the right overhead metric**: Heiser lists "Throughput degraded by x% means overhead is x%" as a crime. If CPU load rises from 60% to 100% and throughput drops 10%, per-unit processing cost rises about 85%, so one should "compare complete CPU load, or processing time per bit for I/O". — [Gernot Heiser: Systems Benchmarking Crimes](https://gernot-heiser.org/benchmarking-crimes.html)
- **Range of loads**: Heiser's "Selective data set hiding deficiencies" warns about an input range chosen to flatter: "the interesting data range starts where the graph ends!" — [Gernot Heiser: Systems Benchmarking Crimes](https://gernot-heiser.org/benchmarking-crimes.html)
- **Loopback is not representative on Windows**: the TCP loopback fast path is used only when an app opts in and no Windows Filtering Platform (WFP) filter is attached. "WFP filters will prevent this new loopback fast path from being used", and `SIO_LOOPBACK_FAST_PATH` "is deprecated and is not recommended". — [Microsoft: SIO_LOOPBACK_FAST_PATH](https://learn.microsoft.com/en-us/windows/win32/winsock/sio-loopback-fast-path); [Microsoft TechNet: TCP Loopback Optimization](https://technet.microsoft.com/library/hh997026.aspx). A MySQL Sysbench test on Windows Server 2012 R2 measured an average 67% TPS increase with the fast path at ≥16 threads (max 86% at 512 threads). — [MySQL blog: loopback fast path on Windows](https://dev.mysql.com/blog-archive/mysql-5-7-labs-using-loopback-fast-path-with-windows-82012/)

### Inferences
- **Recommended run protocol per (framework, scenario, build):**
  1. **Topology.** Use a dedicated client machine with more cores than the server, connected over a real network: back-to-back or through one switch, ideally 25 GbE or faster so the NIC is not the limiter for tiny responses. Confirm with USE checks that client CPU and NIC are not saturated during every run (see Q5). Use loopback only for developer smoke tests, never for published numbers. Loopback removes NIC and IRQ costs, makes client and server share CPUs, and behaves differently per OS (Windows WFP slow path; Linux enables `tcp_tw_reuse` for loopback only).
  2. **Closed-loop saturation sweep** (wrk, cross-checked with bombardier or oha): sweep connections over {16, 32, 64, 128, 256, 512} and add 1024–4096 to find where throughput peaks or degrades. Run pipelined plaintext as a *separate, labelled* scenario at depth 16 for TFB comparability. Report max RPS **and** server CPU-seconds per 1M requests at each level.
  3. **Open-loop latency sweep** (Hyperfoil `constantRate`/`increasingRate`, wrk2 `-R`, or Vegeta `-rate`): run fixed rates from about 10% to 110% of the closed-loop maximum. Size connections or sessions for stalls using the Hyperfoil rule (rate × worst expected stall). Report the percentile spectrum per rate and the MST at the SLO.
  4. **Warm-up and steady state.** Run a primer, then a warm-up at the target load. JIT and GC warm-up specifics are covered by the JVM researcher. Then check stationarity before measuring: per-second throughput and p99 time series should be flat. Discard warm-up data instead of merging it.
  5. **Duration.** At least 60–120 s of steady state per point for p99.9 at ≥10k req/s, and several minutes for p99.99. Use Gregg-style multi-hour soak runs occasionally to catch slow leaks, GC drift and TIME_WAIT build-up.
  6. **Scenario matrix.** Include tiny plaintext and JSON responses (TFB-style); response sizes of about 1 KB, 16 KB, 256 KB and 1 MB; POST bodies; many small headers; slow clients; and a mixed-endpoint scenario. For large payloads report bytes/s and CPU per byte, following Heiser's "processing time per bit".
  7. **Keep-alive vs churn.** Make keep-alive the default. Treat connection churn (`Connection: close` / `--disable-keepalive`) as its own scenario, and size it against TIME_WAIT budgets. When the client closes first, sustainable new connections per (client IP → server IP:port) are roughly ports ÷ TIME_WAIT (arithmetic from the defaults above):

     | OS | Ports ÷ TIME_WAIT | New connections/s |
     |---|---|---|
     | Linux | 28,232 ÷ 60 s | ≈ 470 |
     | macOS | 16,384 ÷ 30 s (2 × 15 s MSL) | ≈ 546 |
     | Windows | 16,384 ÷ 240 s | ≈ 68 |

     Use several client IPs, widen the port ranges, or measure churn on Linux with documented settings. Otherwise the test measures the client OS, not Meleys.
  8. **CPU cost per request.** Sample server process CPU time (user + sys) before and after the steady-state window and divide by completed requests. Report it at fixed offered loads, not only at saturation, because efficiency changes with load. Also report client CPU, to show it had headroom.
- "Throughput at a latency SLO" should be the headline metric for Meleys' "lowest latency" claim. "Max RPS" (closed loop) should be the headline for "highest throughput", always paired with the concurrency level and CPU per request.

## 4. How should the environment be controlled (Linux, cloud, Docker, macOS, Windows)?

### Takeaway
Credible headline numbers come from bare-metal (or dedicated bare-metal cloud) Linux machines with these controls:
- a fixed CPU frequency (performance governor, turbo off);
- SMT and NUMA handled deliberately;
- isolated cores with pinned server, client and IRQ threads;
- tuned socket limits;
- host networking if containers are used;
- every setting recorded.

Public cloud adds instance-to-instance and run-to-run variance, which can be large. Burstable instances are unusable, and A/B comparisons must be interleaved on the same machine.

macOS cannot pin threads to CPUs and ships small socket defaults. Windows' loopback, firewall and antivirus filtering and its long TIME_WAIT distort results. Both are suitable for cross-OS functional and regression checks, with their own documented tuning, but not for headline "fastest" claims.

### Cited Findings

**Linux CPU and kernel controls**
- "On Linux with a multicore CPU, isolating at least 1 core has a significant impact on the stability of benchmarks." pyperf pins worker processes to isolated CPUs and suggests `isolcpus=…` plus `taskset -c`. It also suggests checking context switches in `/proc/pid/status` and the HyperThreading/NUMA topology (`lscpu --extended`, `numactl`). — [pyperf: Tune the system for benchmarks](https://pyperf.readthedocs.io/en/latest/system.html)
- `pyperf system tune` does the following: sets the scaling governor to `performance`; sets `scaling_min_freq` to the maximum; stops `irqbalance` and writes IRQ affinity (`/proc/irq/*/smp_affinity`); disables Turbo Boost (`intel_pstate/no_turbo` or MSR); sets `perf_event_max_sample_rate` to 1; and checks that the machine is on mains power. It also checks that `isolcpus` and `rcu_nocbs` are set, and warns that `nohz_full` is incompatible with the `intel_pstate` driver unless frequency is fixed. — [pyperf system docs](https://pyperf.readthedocs.io/en/latest/system.html)
- LLVM's benchmarking guide recommends: "Disable frequency scaling, Turbo Boost and address space randomization"; set `scaling_governor` to `performance`; use `cset shield -c N1,N2 -k on` and run under the shield; "Disable the SMT pair of the cpus you will use"; "Run the benchmark multiple times to be able to recognize noise"; and avoid storage (use tmpfs). — [LLVM: Benchmarking tips](https://llvm.org/docs/Benchmarking.html)
- **Conflict on ASLR**: LLVM recommends *disabling* address-space randomisation ([LLVM](https://llvm.org/docs/Benchmarking.html)), whereas `pyperf system` *checks that "Full randomization (2) is enabled"* ([pyperf](https://pyperf.readthedocs.io/en/latest/system.html)).

**Linux network and socket controls**
- `somaxconn` (listen backlog limit) "Defaults to 4096. (Was 128 before linux-5.4)". `tcp_max_syn_backlog` is a per-listener SYN_RECV limit: "If server suffers from overload, try increasing this number. Remember to also check /proc/sys/net/core/somaxconn". — [Linux ip-sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html)
- `tcp_tw_reuse`: 0 = disable, 1 = global enable, 2 = loopback only (default 2). `ip_local_port_range` defaults to 32768–60999. — [Linux ip-sysctl docs](https://docs.kernel.org/networking/ip-sysctl.html)
- **Open files**: Vegeta's distributed-attack guide says to "Make sure open file descriptor and process limits are set to a high number for your user **on each machine** using the `ulimit` command." — [Vegeta README](https://github.com/tsenart/vegeta)

**Containers**
- Docker's docs list "To optimize performance" as a use case for host networking: "This is because it doesn't require network address translation (NAT), and no 'userland-proxy' is created for each port." — [Docker docs: Host network driver](https://docs.docker.com/engine/network/drivers/host/)

**Bare metal vs cloud variability**
- **"Taming Performance Variability" (OSDI 2018)**: "software run repeatedly on the same server (or a different server with supposedly identical parts) can produce performance results that differ with each execution". The study gathered "nearly 900,000 data points from 835 servers" over 10 months. It produced a statistical model of "how representative an individual server is of the general population" and a system that makes "recommendations for experiment parameters based on statistical analysis of historical data". The dataset and tools are public. — [USENIX OSDI 2018: Maricq et al.](https://www.usenix.org/conference/osdi18/presentation/maricq)
- **Laaber, Scheuner & Leitner, "Software Microbenchmarking in the Cloud. How Bad is it Really?"** (Empirical Software Engineering, 2019, vol. 24, pp. 2469–2508). The study covered AWS, GCE and Azure (three instance types each) plus IBM Bluemix bare metal, with over 4.5 million data points from Java and Go benchmarks. The coefficient of variation ranged from about 0.03% to over 100% depending on benchmark and instance. Variance came from the benchmark itself, from trials on the same instance, and from differences between instances. Bare metal was very stable, while AWS was typically not much less stable. Running test and control on the same instances in randomised order detected slowdowns of ≤10% with high confidence. — [Chalmers research record](https://research.chalmers.se/en/publication/511491); [ASE 2019 journal-first abstract](https://2019.ase-conferences.org/details/ase-2019-Journal-First-Presentations/9/Software-Microbenchmarking-in-the-Cloud-How-Bad-is-it-Really-); DOI [10.1007/s10664-019-09681-1](https://doi.org/10.1007/s10664-019-09681-1). These details come from the indexed abstract and search summary; Springer's full text was behind an auth redirect.
- **Duet benchmarking**: executing "the measured artifacts in parallel and evaluating their relative performance together" on shared cloud machines improved accuracy "from 2.3x to 12.5x (5.03x on average)" for ScalaBench/DaCapo and "from 23.8x to 82.4x (37.4x on average)" for SPEC CPU 2017. — [Bulej et al., arXiv 2001.05811](https://arxiv.org/abs/2001.05811)
- **Burstable cloud instances**: AWS burstable instances "provide a baseline level of CPU utilization with the ability to burst… governed by CPU credits". In standard mode, when credits run out, CPU "is gradually lowered to the baseline level". — [AWS EC2: Key concepts for burstable performance instances](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-credits-baseline-concepts.html); [AWS EC2: Standard mode](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/burstable-performance-instances-standard-mode.html)
- BenchmarkDotNet's environment analyser warns: "Benchmark was executed on the virtual machine with {hypervisor} hypervisor. Virtualization can affect the measurement result." — [BenchmarkDotNet EnvironmentAnalyser.cs](https://github.com/dotnet/BenchmarkDotNet/blob/master/src/BenchmarkDotNet/Analysers/EnvironmentAnalyser.cs)

**macOS**
- XNU defaults: ephemeral ports 49152–65535 (16,384 ports) — [XNU in.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in.h); `#define SOMAXCONN 128` — [XNU bsd/sys/socket.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/socket.h); MSL 15 s — [XNU tcp_timer.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/tcp_timer.h).
- **No CPU pinning on macOS**: XNU's thread "affinity sets" are scheduler *hints* (sysctl `kern.affinity_sets_enabled` "disables hinting if cleared"). They "are not used on embedded" (affinity sets are enabled by default only for macOS builds). In `thread_policy.c`, the `THREAD_AFFINITY_POLICY` handling returns `KERN_INVALID_POLICY` when affinity sets are disabled, and `KERN_NOT_SUPPORTED` when `thread_affinity_is_supported()` (i.e. `ml_get_max_affinity_sets() != 0`) is false. - Tools on macOS: wrk and wrk2 use kqueue there ([wrk README](https://github.com/wg/wrk); [wrk2 README](https://github.com/giltene/wrk2)). oha installs via Homebrew ([oha README](https://github.com/hatoo/oha)), hey ships macOS binaries ([hey README](https://github.com/rakyll/hey)), and Vegeta documents a macOS install ([Vegeta README](https://github.com/tsenart/vegeta)).

**Windows**
- The dynamic port range defaults to 49152–65535; inspect it with `netsh int ipv4 show dynamicport tcp`. ### Inferences
- **Linux headline-rig checklist:**
  1. Bare metal, or `*.metal`/dedicated hosts; never burstable instances.
  2. Set the `performance` governor and disable turbo/boost (or fix the frequency and record it).
  3. Choose SMT on or off deliberately and use the same choice for all frameworks. When pinning, pin to physical cores and avoid sharing SMT siblings between client-facing IRQ cores and server workers.
  4. Use one NUMA node for server threads, memory (`numactl --cpunodebind --membind`) and the NIC's IRQs.
  5. Stop `irqbalance` and pin NIC queue IRQs to dedicated cores.
  6. Isolate cores (`isolcpus`/`nohz_full`/`rcu_nocbs`, or a `cset`/cgroup v2 cpuset), and run the server with `taskset`.
  7. Raise `ulimit -n` on both ends. Check `somaxconn` (4096 by default since 5.4) and `tcp_max_syn_backlog`.
  8. On the client, widen `ip_local_port_range` for churn tests.
  9. Use `--network host` for containers.
  10. Dump all of the above (kernel version, sysctls, BIOS, NIC firmware) into each result bundle.
- Pick a **single "server profile"** (e.g. N isolated physical cores) and keep it fixed across frameworks. Then add a separate core-scaling sweep (1, 2, 4, 8, … cores), because "fastest" claims depend on core count.
- **Cloud**: use it for breadth and regression detection, not absolute claims. If cloud is used, pin instance type and region/zone (and placement group if available), repeat on several instances (Taming/Laaber), and interleave A/B builds in randomised order on the same instance (Laaber). Treat duet-style co-execution as suitable for CPU-bound micro-benchmarks only. Two HTTP servers sharing one NIC and cache would interfere with each other, which defeats the purpose for network benchmarks.
- **macOS** cannot pin or isolate CPUs, and Apple Silicon P-core/E-core scheduling is outside user control. For macOS runs:
  - raise `kern.ipc.somaxconn` (default 128) and file limits;
  - use long-lived connections (TIME_WAIT is 30 s and only 16,384 ports);
  - plug laptops into power and watch for thermal throttling;
  - expect firewall prompts for new listeners.

  Present macOS results as "works and scales sanely on kqueue", with relative comparisons only, never as headline numbers.
- **Windows** is suitable for checking the IOCP-backed path (via the JDK's Windows NIO implementation; JDK internals are another researcher's area). For Windows runs:
  - use a separate client machine (avoids the WFP-dependent loopback);
  - document firewall and Defender state (WFP callouts affect loopback; Defender's quantitative network impact is unverified);
  - widen the dynamic port range and prefer keep-alive (4-minute TIME_WAIT);
  - set a high-performance power plan;
  - use oha, bombardier, k6, Hyperfoil or Gatling, and avoid wrk via WSL, which adds a virtualisation layer.

  Ideally run Linux and Windows on the *same* hardware, the way crank-style orchestration does for ASP.NET.
- JVM-side controls (heap sizing, GC choice, pre-touch, JIT warm-up) also shape tails. They should be fixed and recorded per run but are covered elsewhere. The same discipline applies to JVM-based clients (Hyperfoil, Gatling), which can inject their own GC jitter into measurements.

## 5. How should results be analysed and reported?

### Takeaway
Treat each run (a fresh server process plus its steady-state window) as one sample. Repeat at several levels (builds, process launches, runs). Report medians with nonparametric or bootstrap confidence intervals and the full spread. Compare builds with interleaved, randomised A/B runs and a rank-based test (Mann–Whitney U / Wilcoxon rank-sum) plus an effect-size confidence interval.

Do active benchmarking (USE on client and server during every run) so each result names its limiter. Avoid Heiser's crimes: give absolute numbers, a baseline, full platform specs, equal tuning for competitors, and geometric means across scenarios. Publish everything needed to reproduce: scripts, versions and raw histograms.

### Cited Findings
- **Heiser's systems benchmarking crimes** — [Gernot Heiser: Systems Benchmarking Crimes](https://gernot-heiser.org/benchmarking-crimes.html):
  - *Selective benchmarking*: not evaluating potential degradation; sub-setting without justification; selective data ranges.
  - *Improper handling of results*: pretending micro-benchmarks represent overall performance; "throughput degraded by x% means overhead is x%"; downplaying overheads (percent vs percentage points, wrong reference point); "No indication of significance". He advises: "Quote standard deviations, use Student's t-test if unsure".
  - *Arithmetic mean across benchmarks*: use the geometric mean.
  - *Wrong benchmarks*: simplified or simulated systems; inappropriate benchmarks; the same data set for calibration and validation.
  - *Improper comparison*: "No proper baseline"; "Only evaluate against yourself"; "Unfairly evaluating competitors" — "using sub-optimal results as a basis for comparison is highly unethical"; not comparing against the state of the art.
  - *Missing information*: platform specification (CPU model, cores, clock, memory, caches, NIC/switch speeds, OS, hypervisor, compiler versions); sub-benchmark results; "Relative numbers only" — "Always give complete result, not just ratios."
- **Gregg's active benchmarking**: analyse "while the benchmark is still running… using other tools" (vmstat, iostat, mpstat, sar, top, tcpdump, perf, bcc/eBPF, strace; `pidstat -t 1` to spot a single-threaded CPU-bound client). Include the suspected limiting factor with results. Good practice is being able to explain why a result was X and not 2X. "A sound statistical method can make benchmark results seem trustworthy, when in fact, they are false… iostat first, R later." — [Brendan Gregg: Active Benchmarking](https://www.brendangregg.com/activebenchmarking.html)
- **USE method**: "For every resource, check utilization, saturation, and errors". Utilization is "the average time that the resource was busy servicing work", saturation "the degree to which the resource has extra work which it can't service, often queued", and errors "the count of error events". Resources to check are CPUs, memory capacity, network interfaces, storage, controllers, interconnects, and software resources (mutexes, thread pools, process/thread capacity, file descriptors). Gregg claims it solves about 80% of server issues with 5% of the effort. Long averages can hide bursts, and any non-zero saturation can be a problem. — [Brendan Gregg: The USE Method](https://www.brendangregg.com/usemethod.html)
- **Multi-level repetition**: Kalibera & Jones say good methodology means running "many iterations of benchmarks, invoke virtual machines (VMs) several times, or even rebuild VM or benchmark binaries more than once". Repetition "is most needed where most uncertainty arises (whether between builds, between executions or between iterations)". Their cost model gives the number of repetitions per level for a target precision, and they show how to "present results with an effect size confidence interval". — [Kalibera & Jones, "Rigorous Benchmarking in Reasonable Time" (ISMM 2013, corrected version)](https://kar.kent.ac.uk/33611/)
- **State of practice in HPC**: of "a stratified sample of 120 papers across three top conferences", "it is often unclear if reported improvements are in the noise or observed by chance". The authors propose "statistically sound analysis and reporting techniques and simple guidelines for experimental design". — [Hoefler & Belli, "Scientific Benchmarking of Parallel Computing Systems" (SC15)](https://htor.inf.ethz.ch/publications/index.php?pub=222)
- **A/B in noisy environments**: randomised-order test/control on the same instances detected ≤10% slowdowns, and the Wilcoxon rank-sum test detected smaller slowdowns than overlapping bootstrapped confidence intervals. — [Laaber et al., EMSE 2019 (Chalmers record)](https://research.chalmers.se/en/publication/511491); [ASE 2019 abstract](https://2019.ase-conferences.org/details/ase-2019-Journal-First-Presentations/9/Software-Microbenchmarking-in-the-Cloud-How-Bad-is-it-Really-)
- **Variability and representativeness**: Taming Performance Variability provides a model of "how representative an individual server is of the general population". Its dataset and tools are public, an example of reproducibility practice. — [USENIX OSDI 2018](https://www.usenix.org/conference/osdi18/presentation/maricq)
- **Confidence-bounded tails**: Lancet reports p99 "with 95% confidence" within ≤10 µs, and flags when tail latency "cannot be accurately measured from a statistical perspective". — [Lancet, USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/kogias-lancet)
- **Histogram merging**: HdrHistograms are additive across threads and time. — [HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram)

### Inferences
- **Statistical protocol for Meleys:**
  1. **Unit of replication.** One run = a fresh server JVM plus a warm-up plus one steady-state window. Do at least 5, preferably 10 or more, runs per configuration. On cloud, spread them over 3 or more instances. Rebuild occasionally to catch build or layout effects (Kalibera & Jones).
  2. **Summaries.** For throughput, report the median across runs with a bootstrap 95% CI, plus min/max or IQR. For latency, report the merged-histogram spectrum *and* the median (with CI) of per-run p99/p99.9. Report means only alongside medians, since throughput and latency distributions are skewed and outlier-prone.
  3. **A/B (two builds or two frameworks).** Interleave ABAB… or randomise the order on the same hardware. Use Mann–Whitney U (Wilcoxon rank-sum) on per-run metrics, and report the effect size: the median ratio with a bootstrap CI. Pre-register a minimum effect of interest (e.g. 2–3%), and call differences inside the CI "no detectable change". With few runs, also show raw per-run dots.
  4. **Across scenarios.** Use the geometric mean of normalised scores (Heiser), and always show per-scenario absolute numbers as well.
  5. **Active benchmarking.** Collect `mpstat`, `pidstat -t`, `sar -n DEV`, `perf stat` (and JFR on the JVM side) on **both** client and server. Annotate each result with its limiter ("server CPU-bound on N cores", "client NIC at 92%", etc.). If the client is the limiter, the result is invalid as a server measurement.
  6. **Fair competitors.** Use the same tuning effort and the same JDK, GC and heap policy. Use each framework's own recommended production configuration, documented, and sanity-check against the framework's published numbers (Heiser).
  7. **Reproducibility bundle per published result.** Include:
     - Git SHAs of Meleys and the benchmark harness;
     - load-generator name, version and commit (important for dormant tools like wrk/wrk2);
     - JDK vendor, build and flags;
     - OS and kernel, sysctl dump, BIOS/power settings, CPU model, core/SMT/NUMA layout, memory, NIC model, firmware and link speed, switch;
     - the exact command lines;
     - raw HdrHistogram logs and per-second time series;
     - the analysis notebooks.

     Publish them alongside the charts so anyone can regenerate them.
- **Regression tracking.** The same A/B machinery (interleaving, rank tests, effect-size CIs) feeds CI regression detection, which another researcher covers. Hyperfoil's FAQ notes that closed-loop max-throughput tests are a good regression signal, even though they are poor latency measurements.
